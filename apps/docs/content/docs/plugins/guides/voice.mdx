Voice is one discriminated contribution family with three common tasks.

This guide describes the 0.3 development Plugin SDK. Declaring a capability is not
a claim that an installed release supports it; runtime and platform admission still
apply.

| Task | Declaration and realm | Runtime import |
| --- | --- | --- |
| Realtime conversation | `kind: 'conversation'`; client leaf | `@happier-dev/plugin-sdk/voice/client` |
| Speech-to-text | `kind: 'speech'` with STT roles; daemon leaf | `@happier-dev/plugin-sdk/voice/speech` |
| Text-to-speech | `kind: 'speech'` with TTS roles; daemon leaf | `@happier-dev/plugin-sdk/voice/speech` |

Realm-neutral declarations and the discriminated runtime contract live at
`@happier-dev/plugin-sdk/voice`. Every runtime is supplied through the same
`voiceProviders.<id>.runtime` author field when its declared realm needs one;
generated activation performs the low-level registration. Give STT and TTS
their own contribution ids when they can be selected independently; do not
recreate the retired `registerSpeech` path or a Voice-local credential/settings
owner.

The host's conversation attempt owns its target, controls and presentation. Top bar,
Island, Orb and Companion consume that same attempt; plugins do not choose placement
or reinterpret Mute, End or Retry. Dictation remains a separate input purpose that
returns editable composer text rather than admitting a conversation turn.

The development Session voice preference reuses the contribution's declared
voice-selection field and settings schema. Preserve its catalog, custom or string
value shape; do not expose a second per-session provider or credential selector.
The host rejects a preference for another contribution or an unrelated setting.
Unknown application stays unknown in current-attempt status, rather than showing
the saved next choice as running audio. Exact-bound instructions and native
carriers remain separate integration requirements; declaring a voice field does
not prove those paths work. Lifecycle Actions retain normal human approval and
captured target/attempt authority.

Credentials declare one slot, effective source, exact host-mediated operation
or raw grant. The host retains source selection, current binding/grant checks,
disclosure approval, cancellation, and materialization. Conversation code must
not use the hosted-web `ui/client` path as a Voice runtime import.

## Privacy facts and numeric controls

In the 0.3 development contract, declare `settings.privacyFacts` alongside the
full `settings.privacyDisclosure`. The facts contain localized
`audioDestination`, `processor`, and `retention`, plus optional `details`.
Use literal service names or `{ key, fallback }` text with a readable fallback.
Describe where microphone audio goes, who processes it, and the actual retention
policy; do not imply a no-training or no-retention guarantee without evidence.
TTS-only services should say that they receive reply text, not microphone audio.

The host renders these facts with its settings rows only on **Settings → Voice →
Privacy & data**. The full disclosure and optional details sit behind **Details**;
plugins do not add privacy banners to the composer or conversation surfaces.

For a contributed numeric settings field, use `kind: 'number'`,
`numericControl: 'stepper'`, a positive `step`, the setting's existing `min`/`max`,
and optional localized `unitKey`. This uses the same numeric draft and stepper as
host settings. Units are presentation only and never become part of saved values.

## Roles decide where a provider is offered

Give your service a recognizable identity with the optional `mark` on its Voice
declaration. For example, ElevenLabs uses the public icon vocabulary:

```ts
import type { VoiceServiceMark } from '@happier-dev/plugin-sdk/voice';

const mark = { kind: 'icon', name: 'waveform' } satisfies VoiceServiceMark;
```

Set `declaration.mark` to that value alongside your contribution's existing
kind, roles and execution declaration. Bundled OpenAI, xAI, ElevenLabs and Codex
use this same public contract.

For a conversation service, add an optional localized `declaration.description`
to explain what it offers in the Service gallery:

```ts
description: {
  key: 'voice.service.description',
  fallback: 'Talk with your assistant using this service.',
},
```

Use your plugin's translations for the key, or a literal string. The description
belongs to the service, so it stays visible when the service offers several
billing choices. Older declarations may omit it. This field is part of the
0.3 development contract.

`VoiceServiceMark` also accepts `{ kind: 'connected_service', serviceId: 'openai' }`
or `{ kind: 'agent', agentId: 'codex' }`. The public
`VoiceServiceMarkSchema` validates the same shapes for installed and bundled
plugins. These marks only identify the service visually; they grant no access to
an Agent, Connected Account or its credentials.

`roles` is not documentation — it is what puts your contribution in a picker.
A speech contribution declaring `dictation_stt` appears in the composer
Dictation provider list; `conversation_stt` and `conversation_tts` appear in
Local voice's speech pipeline. Declare both STT roles only when the same engine
genuinely serves both, and give independently selectable STT and TTS their own
contribution ids.

## Compose Voice schemas

The 0.3 development Voice exports are native `zod/mini` schemas. Use functional
Mini composition when making a field optional or accepting a list:

```ts
import * as z from 'zod/mini';
import { VoiceServiceMarkSchema } from '@happier-dev/plugin-sdk/voice';

const MarksSchema = z.optional(z.array(VoiceServiceMarkSchema));
```

Voice schema declarations expose Mini types, and the SDK's record and
field-composition helpers also produce native Mini schemas. Update and rebuild
consumers that used fluent `.optional()` or `.array()` calls when adopting this
development contract.

## Build a voice-enabled interface

Same-realm Plugin UI surfaces can use `VoiceMarkArt`, `StatusCell`,
`SetupBlockTile`, `SetupBlockGrid` and `SetupSteps` from
`@happier-dev/plugin-ui`. The mark accepts an explicit pose, size, light vector
and light/dark theme. It is still by default; `still={false}` permits pose/light
event transitions, never live microphone energy. `StatusCell` accepts
`working`, `thinking` or `needs_you` and a required accessible label. Both use the
host's existing Brand renderer; they neither subscribe to a Voice attempt nor
decide its state. Reduced-motion and hidden-presentation rules remain host-owned.

Setup tiles use the existing host paper and action controls. The grid owns
in-place opening/closing and mounts its panel only for that lifecycle.
`SetupSteps` is the ordered composition of the shared `HappierStep` marker;
authors supply each step's title, detail, body and current/done/upcoming state.
For progress your plugin reports (a machine being acquired, an install), steps
also take `running`, `waiting` (it needs the reader), `failed` and `cancelled`
and an optional `meta` fact at the row's end; `variant="checklist"` paints one
glyph row per step and `variant="compact"` one quiet line per step for a
popover.
Hosts without these presentation bindings use your explicit `fallback`.
The ordinary `SelectionTiles` wrapper also forwards bare `mark`, translated
`badge`, per-option `testID`, option footers, density, tile sizing, column bounds,
minimum tile width and subtitle lines to the same shared tile owner.

### Show the current conversation

In 0.3 development source, same-realm surfaces can compose the host's live
presentation without choosing its lifecycle or recovery:

```tsx
import { VoicePresence, VoiceMark, VoiceStatusLine, VoiceTransport } from '@happier-dev/plugin-ui/components';

export function CurrentConversation() {
  return <VoicePresence target={{ kind: 'global' }}>
    <VoiceMark size={24} />
    <VoiceStatusLine size="pill" />
    <VoiceTransport size="pill" />
  </VoicePresence>;
}
```

The binding adds no layout and starts no microphone. The mark is visual; Start
still uses the ordinary conversation Action described below. Mute, End, recovery
and dismissal use the current host attempt and normal approval policy. `target`
chooses only an idle Start intent; it cannot retarget an active call.

Inside the binding, `useVoiceAttempt()` returns read-only presentation facts,
including the host's failure sentence, recovery label/icon and exact Agent/Home/
machine target when available. Raw provider errors, prompts, transcripts and
credential configuration are omitted. The public
`VoiceAttemptPresentationSchema` at `@happier-dev/plugin-sdk/voice` validates this
closed shape. A hidden host or `presented={false}` withdraws presentation demand.
Use `fallback` for a host without the same-realm binding; hosted-web frames do
not gain live Voice rendering through this API.

Providers may decline preparation or throw a safe `code`. For example,
`agent_signed_out` selects the host's Agent sign-in recovery in either path;
credential-unavailable codes retain credential review. Use the public failure
taxonomy for supported host kinds, and leave labels, routes and retry policy to
the host. These additions are development source, not published-host availability.

### Dictate into your own input

The public `TextField` accepts `dictation` to place the host's Dictation control
beside your controlled input. It follows the field's disabled state and returns
editable text through `onTranscription`. Decide how to insert those words, and
keep submission as a separate user action:

```tsx
import { useState } from 'react';
import { Text, TextField } from '@happier-dev/plugin-ui';

export function DraftInput() {
  const [draft, setDraft] = useState('');
  return <TextField label="Draft" value={draft} onChange={setDraft} multiline
    dictation={{
      onTranscription: (words) => setDraft((current) => current ? `${current}\n${words}` : words),
      fallback: <Text>Dictation is unavailable in this host.</Text>,
    }} />;
}
```

This uses the composer's Dictation engine, recognition language, microphone
permission, capture admission and error handling. It is independent of the
selected conversation service, and does not create a Session target. The host
cancels capture and rejects late delivery when the field's control is hidden,
disabled or unmounted. `presented={false}` and `disabled` may narrow admission;
they cannot override hidden host presentation. Remount the control with a new
React key when replacing the logical draft it edits. Do not send audio to a
second STT implementation from your UI. Hosted-web frames without the same-realm
presentation binding retain their normal text input and use the fallback.
For a custom input, compose the public `DictationButton` beside it with the same
delivery callback and bind its `disabled` prop to that input's editability.

## Commands a voice agent can call

Declare an ordinary plugin Action through `definePlugin({ actions: ... })` and
include `voice` in its invocation surfaces. Give it a typed input/output schema,
accurate effect/safety metadata and, when useful, `definition.examples.voice`.
The host's `action.spec.search`, `action.spec.get` and `action.invoke` tools
discover and dispatch it through the same Action policy, approvals and target
ownership as other invocation surfaces. A Tool declaration's separate
`cli`/`mcp`/`agent` surface grammar does not create a Voice tool.

A mounted UI may publish contextual commands with
`hostApi.publishCurrentUiContext({ commands: [...] })`: a command describes an
admitted `executeAction` or `openSurface` operation. Host-generated command
handles, privacy filtering and synchronous retirement stay with the mounting
client. These commands describe that foreground interface, not another client
on the Account.

For a conversation provider, `VoiceClientToolDefinition` at
`@happier-dev/plugin-sdk/voice/client` describes the host-delivered tools in
realtime preparation. Adapt their names, descriptions and parameter schemas to
your native provider. Its `execute` callback is an attempt-bound read boundary,
not a new plugin registration API: effects must emit canonical `tool_calls` with
the declared correlation capability so the host Action barrier can authorize,
cancel and settle them. Never bypass that barrier or manufacture an approval
token; Voice approval delegation is enforced by the host's existing decision owner.

### Start a conversation or Brief

Use `usePluginHostApi().executeAction` rather than an app-internal Voice controller:

```ts
await hostApi.executeAction('ui.voice_global.start', {
  target: { kind: 'global' }, expectedAttempt: null,
});
await hostApi.executeAction('ui.voice_global.brief.request', {});
```

These development Actions are contributed by the Voice Actions owner. Starting
or recovering microphone input and requesting/retrying a Brief require ordinary
host approval by default. Inspect the typed result instead of assuming speech
started: unsupported microphone hosts or an unmounted/unready Home/Inbox Brief
owner can return unavailability or refusal. `ui.voice_global.get` supplies the
captured attempt identity for subsequent end/mute/hold operations; navigation
must not retarget them. Dictation does not start one of these conversations.

## The host owns the transcript, not your runtime

A `direct_media` conversation runtime does not decide where its turns are
persisted. The host resolves that per attempt: an attempt with a target session
writes into that session's transcript, and a targetless one writes into the one
account-wide Voice History carrier shared by every such provider. An
`experimental_agent_session_realtime` runtime binds `native_session` instead, so
the Agent session itself carries the conversation.

External and bundled conversation providers go through the same runtime host and
the same acquisition path, so a plugin you install gets identical transcript,
tool, cancellation and retirement behaviour to a bundled one.

The [contribution reference](/plugins/manifest/contributions#voice-providers)
and the public-authoring example contain full conversation, STT, and TTS
shapes.

## Attempt policy and human approval

Standalone realtime preparation can consume the host's optional `attemptPolicy`.
It contains the admitted reply-language, greeting and client-tool guidance, and the
host retains it through reconnect. Translate supported policy into your provider's
native configuration; do not advertise an independent language or greeting control
unless the runtime applies it. Attached Agent sessions retain their session-owned
prompt authority.

For an immediate greeting, the policy may include `welcome.text`, translated in
the admitted reply language. Use that value for a provider's literal first-message
override; Off and After I speak carry no immediate text. If no literal is available,
retain the policy's model-generated greeting instructions. A provider that can
only start with a literal should wait for the user and declare
`immediateRequiresLiteral: true` on its curated `welcome` field so the host
explains that limitation.

Speech can describe a permission request only within the person's context-sharing
policy. In **0.3 development**, **Voice agent can approve requests** defaults on for
Local Voice and realtime modes exposing host decision tools: the Voice agent can
approve or deny any pending request on the person's behalf
through the existing host decision owner. Prompt guidance tells it to read the
request, ask, and follow the answer. Decisions are attributed to the Voice agent
acting for the person. With the setting off, decisions require a tap in the request
UI; a provider must preserve the host's refusal. Other automated callers keep
their existing authority floors. Plugins cannot create confirmation tokens or
decide outside that owner. End retirements do not settle pending permissions.
Tool effects still enter the host's canonical Action barrier with captured attempt
identity and currentness. This describes development source, not released availability.

Native Codex Realtime is explicitly excluded: it keeps native delegation and
exposes only current-UI host tools. Its agent should read the request within the
sharing policy, state that it cannot approve or deny it there, and direct the
person to tap the request or switch to Local Voice. The setting does not expand
the provider's tool surface or the attached Agent's authority.

For speech output, declare provider input budgets through the public speech
declaration. Character and UTF-8 byte limits are distinct. The host uses those facts
to batch whole and streaming replies in order; runtime leaves must not invent a
second playback or segmentation policy.

## Current UI context

“Current UI” means the foreground, mounted interface of the exact client that
hosts the active Voice attempt. It never means another phone, browser tab, or
desktop client on the Account.

Every admitted app route contributes a parameter-free navigation baseline.
That baseline identifies a stable area and screen pattern without copying
dynamic route values, query or hash data, raw URLs, IDs, paths, tokens, form
values, modal content, or other page input. Canonical Settings, Session,
machine, plugin-page, modal, mobile-tab, and explicit-pane owners may enrich
that baseline. A mounted product or plugin surface may additionally provide
bounded semantic entity/detail data and contextual commands for only its
mount lifetime; retirement removes that enrichment synchronously.

Voice's independent `currentUiContextMode` privacy setting defaults to
`on_demand` and has three source contract values:

| Mode | Disclosure contract |
| --- | --- |
| `off` | Expose no current-UI read or command tool, and send no automatic updates. |
| `on_demand` | Advertise an explicit current-UI read; send no automatic updates. |
| `automatic` | Keep that explicit read, add best-effort metadata-only navigation transitions, and announce the session the user opens on this client. |

Disclosure and command availability are separate. A read can disclose opaque
contextual-command descriptors, but the `invokeCurrentUiCommand` tool is
advertised only when the active Voice provider and attempt support the existing
stable effect-custody contract. Enabling `on_demand` or `automatic` does not
weaken that capability gate.

Automatic transitions contain admitted navigation metadata such as area,
screen, presentation, and a title supplied by the host's canonical navigation
owner. A title published by a mounted plugin remains plugin-provided semantic
content and is disclosed only by an explicit current-UI read, alongside entity
summaries, detail, form content, and command payloads. Automatic updates are
ephemeral: they are not persisted, synchronized, replayed across restarts, or
ordered across clients.

Opening a session on this client is the same kind of observation — nothing but
the user navigating here produces it — so the session-focus announcement
answers to this mode rather than to a second switch. `off` and `on_demand` send
no announcement at all; under `automatic` the announcement carries only the
session context the Voice sharing settings already permit, and a session whose
update level is `none` still contributes nothing.

Contextual command ids are opaque and scoped to the current snapshot. The
invoking client resolves them again immediately before execution, then
delegates to the existing Action or navigation owner. Confirmation, effect
custody, cancellation, currentness, result redaction, and no-blind-retry rules
remain unchanged. A stale command or retired surface has no effect, and
client-local work has no daemon or cross-client fallback.

Maintained built-ins and the prepared packed-external fixture use the same
public declaration, `activate(api)`, currentness, navigation, and Action paths.
They remain trusted executable package code; this is not a new plugin sandbox
or a privileged built-in Voice route. Exact packed and loaded parity is still
part of the open proof named above.
